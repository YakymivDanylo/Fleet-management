# RFC-001 · Песимістичне блокування рядка авто (`SELECT … FOR UPDATE`) при старті оренди

## 1. Заявка

| Поле | Значення |
|---|---|
| Ідентифікатор | RFC-001 · трекер: [issue #53](https://github.com/YakymivDanylo/Fleet-management/issues/53) |
| Ініціатор, дата | Danylo Yakymiv (розробник), 2026-11-20 |
| Опис | `rental_service.start_rental` читає авто через `db.get(Vehicle, id, with_for_update=True)`: рядок `vehicles` блокується до кінця транзакції, тож друга одночасна спроба орендувати те саме авто чекає, бачить `rented` і отримує 409 |
| Мета | гарантувати інваріант SDD §4 «одне авто — одна активна оренда» на рівні БД |
| Обґрунтування | **бізнес:** подвійна видача одного авто = два клієнти біля однієї машини, компенсації, втрата довіри; у пікові години конкуренція за останнє авто на популярній станції — штатний сценарій навантаження (README, ЛР№1). **Архітектура:** закриває відоме обмеження з аудиту ЛР№10, ADR-0001 (наслідки) і [[adr-0005-row-lock-on-rental-start\|ADR-0005]] |
| Доказ проблеми | `tests/integration/test_rental_concurrency.py` на поточному коді: два одночасні `start_rental` → `['201', '201']` (`docs/lab12/evidence/rfc001_race_before.txt`) |
| Клас зміни (ITIL) | **нормальна** — не стандартна (зміна коду критичного шляху, не попередньо схвалений шаблон), не термінова (інциденту в production ще не було) |
| Клас ризику | **середній** (Risk Exposure 8 з 25, §3) |
| Вікно розгортання | субота 2026-11-21, 22:00–23:00 UTC (мінімум оренд; узгоджене вікно обслуговування з `slo.yaml`) |

## 2. Impact Analysis — сім рівнів впливу

| Рівень | Що зачіпається | Конкретні артефакти | Оцінка |
|---|---|---|---|
| **1. Вимоги** | сценарій «Орендар починає оренду» (UC старту оренди): при одночасних запитах на останнє авто тепер рівно один отримує 201, інший — 409 «Vehicle N is not available» замість «успішної» дублікатної оренди | README (сценарій навантаження), `docs/api/openapi.yaml` → `startRental` (409 уже задокументовано) | поведінка для одиночних запитів **не змінюється** |
| **2. Архітектура** | компонент API → `services/rental_service.py` → PostgreSQL; новий зв'язок не з'являється, змінюється спосіб читання рядка | [[sdd#4-модель-даних\|SDD §4]] (прибрати «відоме обмеження»), [[adr-0005-row-lock-on-rental-start\|ADR-0005]] Proposed → Accepted | новий ADR **потрібен** — це рішення про модель конкурентності (оформлено ADR-0005) |
| **3. Код** («радіус ураження») | 1 рядок виробничого коду | `src/fleet_management/services/rental_service.py` (`start_rental`); `tests/integration/test_rental_concurrency.py` (новий); `tests/unit/test_goodhart_rentals.py` (сигнатура `db.get`) | малий радіус: 1 функція, 1 ендпоінт |
| **4. API** | `POST /rentals/start` — схема запиту/відповіді і коди не змінюються | `openapi.yaml`: уточнення опису 409 (конкурентний запит) | **additive / non-breaking** → PATCH `1.0.0 → 1.0.1`; міграційний гайд не потрібен |
| **5. Дані** | міграції схеми **немає**; блокування рядка — лише під час транзакції (мілісекунди) | `alembic/versions` — без змін | повністю зворотно (відкат = попередня версія коду) |
| **6. Тести** | мінімальний регресійний набір | `tests/integration/test_rental_concurrency.py`, `tests/integration/test_api.py` (усі `*rental*`), `tests/unit/test_goodhart_rentals.py`, `tests/unit/test_rental_service.py`, Schemathesis (`startRental`), quality-gate (coverage ≥ 90 % AND mutation ≥ 75 %) | без нових фікстур; потрібен Postgres (integration) |
| **7. Документація та експлуатація** | DoD «docs-or-don't-merge» | SDD §4, ADR-0005, `openapi.yaml` (опис 409, версія), `CHANGELOG.md`, [[alert-catalog\|ALR-01]] — спостереження після релізу, SLI-2 latency `/rentals*` — спостереження 24 год; runbook-и не змінюються | 5 документів |

## 3. Оцінка ризику (Risk Exposure)

Risk Exposure = Імовірність збою × Величина наслідків (шкала 1–5 кожна, максимум 25):

| Ризик | Імовірність | Наслідки | RE |
|---|---|---|---|
| Очікування блокування збільшує латентність `POST /rentals/start` у пік (черга запитів на одне авто) | 2 — блокування тримається мілісекунди, конкуренція за **одне** авто рідкісна | 4 — старт оренди — ключова функція, витрачається бюджет SLI-2 | **8** |
| Взаємоблокування (deadlock) | 1 — транзакція блокує один рядок, порядок блокувань однаковий | 4 | 4 |
| Регресія одиночного старту оренди | 1 — покрито integration-тестами | 5 | 5 |

Підсумковий клас ризику — **середній** (максимальний RE = 8). Кількісно: імовірність 10 % × до 60 хв деградації
старту оренд ≈ 6 хв очікуваних втрат бюджету SLI-2 (бюджет — 432 хв/міс, [[slo-policy]]).
