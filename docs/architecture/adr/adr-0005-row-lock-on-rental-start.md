# ADR-0005: Песимістичне блокування рядка авто (`SELECT … FOR UPDATE`) при старті оренди

- **Статус:** Proposed
- **Дата пропозиції:** 2026-11-20
- **Автор / власник:** Danylo Yakymiv
- **Пов'язані документи:** [[sdd#4-модель-даних|SDD §4]] (відоме обмеження),
  [[adr-0001-postgresql-redis-rabbitmq-storage|ADR-0001]] (наслідки), [[handover]] (план Bus Factor, захід 2)

## Контекст

`rental_service.start_rental` читає авто через `db.get(Vehicle, id)`, перевіряє `status == available` і в тій самій
транзакції ставить `rented`. Між читанням і записом рядок не заблокований: два одночасні запити на останнє вільне
авто можуть обидва пройти перевірку (READ COMMITTED), і з'являться дві активні оренди одного авто — порушення
інваріанта SDD §4. Обмеження зафіксовано аудитом ЛР№10 і в README.

## Розглянуті альтернативи

| # | Варіант | Плюси | Мінуси |
|---|---|---|---|
| A | **`SELECT … FOR UPDATE` на рядок `vehicles`** | мінімальна зміна (один виклик), інваріант гарантує БД; другий запит чекає і бачить `rented` → 409 | блокування рядка на час транзакції (мілісекунди) |
| B | Оптимістичне блокування (`version`-колонка) | без очікування | міграція схеми, повтор на клієнті, більше коду |
| C | Частковий унікальний індекс `rentals(vehicle_id) WHERE status='active'` | інваріант на рівні схеми | міграція; конфлікт видно як `IntegrityError` → треба мапити в 409 |
| D | Нічого не робити | — | ризик подвійної видачі авто в пікові години |

## Рішення (запропоноване)

Варіант A; варіант C — кандидат на окреме рішення як другий рубіж захисту. Зміна оформлена як заявка на зміну
RFC-001 (ЛР№12) і чекає рішення Change Control Board.

## Наслідки (очікувані)

- ✅ Інваріант «одне авто — одна активна оренда» тримається на рівні БД.
- ⚠️ Під високою конкуренцією за одне авто запити серіалізуються — латентність p95 цього ендпоінта зростає.
