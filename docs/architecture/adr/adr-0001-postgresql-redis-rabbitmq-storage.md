# ADR-0001: PostgreSQL як джерело істини, Redis для гарячого стану, RabbitMQ для телеметрії

- **Статус:** Accepted
- **Дата рішення:** 2026-09-04 (ЛР№1, вибір стеку); реалізація — 2026-09-16 (telemetry worker, коміт `b18d110`)
- **Дата запису:** 2026-11-14 (оформлено з обґрунтування README ЛР№1 та комітів реалізації)
- **Автор / власник:** Danylo Yakymiv
- **Пов'язані документи:** [SDD §3.4–3.7](../sdd.md#c-worker), [ISD §4, §7](../isd.md#isd-storage)

## Контекст

Система має два різні профілі навантаження:

1. **Транзакційні дані** (станції, авто, орендарі, оренди) — малий обсяг, але жорсткі інваріанти:
   авто не можна видати двом орендарям, на станції не може стояти більше авто, ніж місць.
2. **Телеметрія** — безперервний потік від кожного авто (координати, пальне, замок) з піковими сплесками;
   API має швидко віддавати *останній* стан авто, а історія потрібна лише для аналітики та fallback.

Якщо телеметрію писати синхронно через API в ту саму БД, сплески запису блокують пул з'єднань і
погіршують латентність бронювань.

## Розглянуті альтернативи

| # | Варіант | Плюси | Мінуси |
|---|---|---|---|
| A | **PostgreSQL + Redis + RabbitMQ** (обрано) | ACID і зовнішні ключі для оренд; брокер згладжує піки й розв'язує сенсори і запис у часі; Redis дає O(1) читання гарячого стану | три інфраструктурні компоненти, складніший локальний запуск і моніторинг |
| B | Лише PostgreSQL (телеметрія через `POST` в API) | один компонент, проста експлуатація | пікові записи конкурують з бронюваннями; читання «останнього стану» = важкий запит до великої таблиці |
| C | MongoDB/документна БД для всього | гнучка схема телеметрії | немає транзакційних інваріантів між оренда/авто/станція без додаткових механізмів; команда знає SQL краще |
| D | PostgreSQL + Kafka замість RabbitMQ | ретеншн і реплей потоку | надмірно для масштабу курсового проєкту, важчий у локальному запуску та в minikube |

## Рішення

- **PostgreSQL 16** — єдине джерело істини для всіх сутностей і історії телеметрії; схема — Alembic.
- **RabbitMQ** — черга `telemetry`; запис виконує окремий процес `telemetry-worker` (ідемпотентно,
  `ON CONFLICT DO NOTHING` за `(vehicle_id, recorded_at)`), щоб доставка «at-least-once» була безпечною.
- **Redis** — лише похідні дані (`vehicle:{id}:state`, кеш списків); API читає Redis, а при його
  недоступності переходить на останній запис PostgreSQL з ознакою `degraded=true`.

## Наслідки

- ✅ Латентність бронювань не залежить від інтенсивності телеметрії; worker масштабується окремо.
- ✅ Втрата Redis не втрачає даних (RPO n/a, див. ISD §7); бекапиться тільки PostgreSQL.
- ⚠️ Потрібні healthcheck-и і порядок старту (ISD §2.1), моніторинг трьох сховищ; локальний запуск —
  лише через Docker Compose.
- ⚠️ Eventual consistency: стан у Redis може відставати від реальності на час проходження черги.
- ⚠️ Інваріант «одне авто — одна активна оренда» тримається на перевірці статусу в сервісі без
  `SELECT … FOR UPDATE` (див. SDD §4) — кандидат на наступний ADR, якщо з'явиться конкурентне навантаження.
