# RB-002 · Backlog черги `telemetry` / застаріла телеметрія

Створено як коригувальна дія **CAPA-2** після [[INC-001]]: до інциденту збій інжесту телеметрії не мав ні алерта, ні
інструкції — його виявила людина випадково.

| Поле | Значення |
|---|---|
| Ідентифікатор | RB-002 |
| Рівень автоматизації | **1 — скриптований**: перевірка — `scripts/telemetry_check.py`, дії — команди нижче |
| Власник | SRE on-call (L2); код worker'а — L3 ([[telemetry-worker]]) |

## Тригер

| Алерт | Умова |
|---|---|
| `ALR-05 TelemetryQueueBacklog` ([[alert-catalog]]) | `python scripts/telemetry_check.py` повертає 1: `messages_ready` черги `telemetry` > 500 **або** найновіший показник у PostgreSQL старший за 60 с (SLI-3) протягом 2 перевірок поспіль (2 хв) |

## Передумови

Доступ до Docker-хоста і `.env.<env>`; Python 3.13; доступ до RabbitMQ Management API (порт `RABBITMQ_MGMT_PORT`).

## Кроки

1. **Підтвердити** і зафіксувати час (UTC) в `#fleet-incidents`:
   `python scripts/telemetry_check.py --project fleet_production --env-file .env.production`.
2. **Залежності worker'а** — усі мають бути `healthy`:
   `docker compose -p fleet_production --env-file .env.production ps db redis rabbitmq worker`.
3. **Логи worker'а**: `docker compose -p fleet_production --env-file .env.production logs worker --since 10m | Select-String "ERROR|WARNING"`.
   - `Vehicle state cache unavailable` (після CAPA-1) — Redis лежить, **інжест у PostgreSQL триває**: відновити Redis
     (`… up -d redis`), черга не росте — це SEV-3.
   - `Failed to process telemetry, requeueing` — недоступна PostgreSQL або «отруйне» повідомлення: перевірити `db`
     (за потреби — [[RB-001]]); при одному й тому самому повідомленні в циклі — ескалація L3 (немає DLQ, TD-2).
   - Немає логів обробки / контейнер перезапускається — `docker compose … up -d --force-recreate worker`.
4. **Дренування**: після усунення причини черга спорожняється сама; за 200+ повідомлень/с одним worker'ом —
   тимчасово масштабувати: `docker compose … up -d --scale worker=3` (ідемпотентний INSERT робить паралельну обробку безпечною).

## Верифікація

`python scripts/telemetry_check.py` → `telemetry pipeline: PASS` (черга < 500, свіжість ≤ 60 с) двічі поспіль з
інтервалом 1 хв; `GET /vehicles/{id}/state` → `degraded: false`, `recorded_at` оновлюється.

## Відкат

Кроки 2–4 не змінюють дані; масштабування повертається `--scale worker=1`. Видаляти повідомлення з черги
(`purge`) **заборонено** без рішення L3: це безповоротна втрата телеметрії.

## Ескалація

| Умова | Кому | Таймаут |
|---|---|---|
| Черга не зменшується після кроку 3 | L3 — власник `telemetry-worker` | 15 хв |
| Свіжість > 60 с понад 30 хв (витрачено ≥ 7 % місячного бюджету SLI-3) | Incident Commander, SEV-2 | 30 хв |
