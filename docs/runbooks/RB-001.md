# RB-001 · Відновлення PostgreSQL з резервної копії (Restore)

| Поле | Значення |
|---|---|
| Ідентифікатор | RB-001 |
| Операція | Відновлення бази `fleet_<env>` з логічної копії `pg_dump -Fc` (повне) або перевірочне відновлення (restore drill) |
| Середовище | Docker Compose (`fleet_sandbox`, `fleet_production`); для k8s — ті самі команди через `kubectl exec` ([[isd#isd-k8s\|ISD §2.2]]) |
| Рівень автоматизації | **1 — скриптований** (`scripts/db_backup.py`), див. [обґрунтування](#рівень-автоматизації) |
| Цільові RTO / RPO | 30 хв / 24 год (поточна політика) — розрахунок у [[isd#isd-rto-rpo\|ISD §8.4]] |
| Власник | SRE on-call (L2); ескалація — [[maintenance-plan#матриця-ескалації\|матриця ескалації]] |

## Тригер

Runbook застосовується, коли спрацював один з алертів [[alert-catalog|каталогу]] і діагностика показала втрату або
пошкодження даних, а також планово:

| Тригер | Алерт / подія | Розділ runbook |
|---|---|---|
| БД недоступна і не піднімається перезапуском (пошкоджений том `pgdata`, `PANIC` у логах) | `ALR-02 FleetDatabaseDown` | [Повне відновлення](#б-повне-відновлення-production) |
| Дані зіпсовано (помилкова міграція, масове видалення) — скарга користувачів / 5xx після релізу | `ALR-01 FleetHighErrorRate` + підтвердження в даних | [Повне відновлення](#б-повне-відновлення-production) |
| Немає свіжої копії > 26 год | `ALR-03 FleetBackupStale` | [Резервна копія](#а-резервна-копія-зараз) |
| Щомісячна перевірка копій (1-й робочий день місяця, 10:00 UTC) | планове розкладання | [Restore drill](#в-restore-drill-щомісяця) |

## Передумови

- Доступ: SSH на Docker-хост середовища; членство в групі `docker`; файл `.env.<env>` (секрети — у сховищі паролів команди).
- Інструменти: Docker Compose v2, Python 3.13 (`scripts/db_backup.py` — лише stdlib), Git checkout репозиторію.
- Копії: каталог `backups/` на хості (копія 1), об'єктне сховище поза майданчиком (копія 3) — [[isd#isd-backup\|ISD §7]].
- Комунікація: повідомлення в канал `#fleet-incidents` **до** початку відновлення production (дані після RPO буде втрачено).

## Кроки

### А. Резервна копія «зараз»

```powershell
python scripts/db_backup.py backup --project fleet_production --env-file .env.production
# -> backups/fleet_<UTC>.dump + .dump.sha256
python scripts/db_backup.py prune --keep-daily 7 --keep-weekly 4      # retention
```

### Б. Повне відновлення (production)

1. Зафіксувати час початку (UTC) в інцидент-каналі; оголосити режим обслуговування.
2. Вибрати копію: остання з `backups/` або завантажена з off-site (`backups/fleet_YYYYMMDDTHHMMSSZ.dump`).
   Скрипт сам перевірить SHA-256 — пошкоджена копія відхиляється.
3. Відновити (скрипт зупиняє `api1..3` і `worker`, відновлює БД `--clean --if-exists`, піднімає застосунок у
   порядку залежностей: **спершу БД, потім застосунок**):

   ```powershell
   python scripts/db_backup.py restore --project fleet_production --env-file .env.production `
       --dump backups/fleet_20261120T115013Z.dump
   ```

4. Якщо копія старша за поточну схему — накотити міграції: `docker compose -p fleet_production --env-file .env.production run --rm migrate`.

### В. Restore drill (щомісяця)

```powershell
python scripts/db_backup.py drill --project fleet_production --env-file .env.production
```

Свіжа копія відновлюється в одноразовий контейнер `postgres:16-alpine`; кожна таблиця порівнюється з джерелом.
Результат (`restore drill: PASS/FAIL`, час `pg_restore`) додається до журналу drill в [[isd#isd-restore-drill\|ISD §7.3]].

## Верифікація

| Перевірка | Команда | Очікувано |
|---|---|---|
| Застосунок здоровий | `docker compose -p fleet_production ps` | усі сервіси `healthy` |
| БД відповідає | `curl -s http://localhost:8080/health` | `{"status":"ok","db":"connected"}` |
| Схема на місці | `docker compose -p fleet_production exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Atc "select version_num from alembic_version"'` | поточний head Alembic |
| Дані є | `curl -s http://localhost:8080/stations` і `GET /stations/{id}/availability` | непорожній список, коректні `free_slots` |
| Телеметрія знову пишеться | `GET /vehicles/{id}/state` двічі з інтервалом 30 с | `recorded_at` зростає, `degraded: false` |
| Drill | вивід скрипта | `restore drill: PASS` |

## Відкат

Відновлення руйнівне (`--clean`), тому **перед кроком Б.3** виконується крок А (копія поточного, навіть
пошкодженого стану). Якщо після відновлення верифікація не проходить — повторити Б.3 з цією копією (повернення
до стану «до відновлення») і ескалювати. Відкат drill не потрібен: він не торкається робочої БД.

## Ескалація

| Умова | Кому | Таймаут |
|---|---|---|
| Restore не завершився або верифікація не проходить | L3 — власник БД / архітектор (`@YakymivDanylo`) | 15 хв від початку кроку Б |
| Немає жодної цілої копії (усі SHA-256 не збігаються) | L3 + продуктовий власник (рішення про втрату даних) | одразу |
| Час простою наближається до RTO 30 хв | Incident Commander, комунікація клієнтам (SLA) | на 20-й хвилині |

## Рівень автоматизації

Обрано **рівень 1 (скриптований)**: усі кроки — одна команда `db_backup.py`, але **рішення** про відновлення
приймає людина. Рівень 2 («одна кнопка», напр. workflow_dispatch) і 3 (self-healing) тут небезпечні: restore
руйнує поточні дані і переводить систему на стан до RPO — помилкове автоматичне спрацювання на хибному алерті
знищило б більше даних, ніж сам збій. Drill, навпаки, безпечний — його кандидат на рівень 2 (щомісячний cron у CI)
внесено в [[maintenance-plan]].
