# Регламент підтримки документації

## 1. Головне правило

> **Зміна коду = зміна документації.** Жодне злиття в `main` не проходить без оновлення документів,
> які описують змінену поведінку, структуру чи розгортання.

| Що змінилось у PR | Що оновити в тому ж PR |
|---|---|
| Новий/змінений HTTP-ендпоінт, формат відповіді, контракт телеметрії | `docs/sdd.md` §5 (+ README, якщо змінилась поведінка для користувача) |
| Новий компонент, модуль, таблиця, міграція | `docs/sdd.md` §2–4 (C4-діаграма, компонент, модель даних) |
| `docker-compose*.yml`, `Dockerfile*`, `nginx/`, `charts/`, `argocd-apps/`, `.github/workflows/` | `docs/isd.md` (топологія, порядок старту, змінні, CI/CD) |
| Нова змінна оточення | `docs/isd.md` §1.1 + `.env*.example` |
| Нове архітектурне рішення / відмова від старого | новий ADR у `docs/architecture/adr/` (старий → `Superseded by`) |
| Будь-яка завершена зміна | `CHANGELOG.md` |

**Як це забезпечено:**

1. CI-job `docs-currency` (`.github/workflows/ci.yml`) запускає `python scripts/doc_audit.py --strict`:
   падає, якщо HTTP-маршрут з `src/fleet_management/api` не описаний у SDD, є биті відносні посилання,
   документ відсутній, застарів (> 180 днів) або після його оновлення накопичилось > 20 комітів коду.
2. PR-шаблон `.github/pull_request_template.md` — обов'язковий чекбокс «документацію оновлено / не потрібно, бо…».
3. Ревʼюер перевіряє відповідність таблиці вище; документи з порушеним циклом перегляду — блокер релізу.

## 2. Цикли перегляду

Пороги — з аудиту ЛР№10 (Завд. 1): > 90 днів без оновлення — підозрілий документ, > 180 — застарілий.

- **Експлуатаційна** документація — не рідше ніж раз на **90 днів**.
- **Архітектурна** — раз на **180 днів**.
- **Документи процесу** (CHANGELOG, звіти) — не переглядаються: це історичні записи; CHANGELOG лише доповнюється.

> Резервний власник (co-owner) призначається першим, щойно в команді з'являється друга людина.

## 4. Процедура перегляду

1. `python scripts/doc_audit.py --today <дата>` — зняти метрики (вік, drift, биті посилання, маршрути).
2. Для кожного документа з вердиктом WARN/FAIL ухвалити рішення: **оновити / видалити / deprecated**
   (deprecated = банер зверху з датою і посиланням на заміну; файл більше не оновлюється).
3. Оновити колонку «Дата останнього перегляду» в таблиці §3 і поле `last_review` у front matter документа.
4. Закомітити: `docs(maintenance): periodic review <YYYY-MM-DD>`.
