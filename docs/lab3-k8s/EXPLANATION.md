# Пояснення виконаної роботи — Лабораторна №3 (Kubernetes)

Документ пояснює, **що** зроблено, **навіщо** і **чому саме так**, а не інакше. Результати виконання команд — у [`REPORT.md`](REPORT.md).

## 1. Базові терміни

| Термін | Що це |
|---|---|
| **Кластер / Node** | Набір машин під керуванням Kubernetes. У minikube — один вузол у Docker-контейнері. |
| **Pod** | Найменша одиниця: один або кілька контейнерів зі спільною мережею (одна IP) і томами. Под «смертний» — його замінюють новим з іншим іменем та IP. |
| **ReplicaSet** | Підтримує задану кількість однакових подів. |
| **Deployment** | Керує версіями: при зміні шаблону створює новий ReplicaSet і поступово переносить на нього поди; старий зберігає для відкату. |
| **Service** | Стабільне DNS-ім'я та віртуальна IP для групи подів (`postgres`, `api`…). |
| **Label / Selector** | Мітки на об'єктах і фільтр за ними. Так Deployment знаходить свої поди, а Service — куди слати трафік. |
| **Namespace** | «Папка» в кластері, що ізолює імена й об'єкти. |
| **ConfigMap / Secret** | Несекретні / чутливі параметри конфігурації. Secret зберігається в base64 (це **не** шифрування) — захищається окремими правами доступу (RBAC) і не показується в `describe`. |
| **PV / PVC / StorageClass** | Диск / заявка на диск / «постачальник», що створює диск під заявку автоматично. |
| **Ingress** | HTTP-маршрутизатор (L7) за доменом і шляхом. Працює лише з Ingress-контролером (тут — nginx). |
| **Probe** | Періодична перевірка контейнера, яку виконує kubelet. |
| **requests / limits** | Гарантовані ресурси (за ними планувальник обирає вузол) / стеля. Перевищення memory-limit → `OOMKilled`, CPU-limit → сповільнення. |
| **Декларативний підхід** | Описуємо бажаний стан у YAML (`kubectl apply`); Kubernetes сам приводить реальний стан до нього (*reconciliation loop*). |

## 2. Зміни в коді застосунку

### `/livez` і `/info` (`src/fleet_management/main.py`)
- **`/livez`** — liveness-перевірка «процес живий?». Навмисно **без** звернення до БД. Існуючий `/health` робить `SELECT 1`; якби він був liveness-пробою, падіння Postgres призвело б до перезапуску **всіх** подів API по колу — а перезапуск не лікує недоступну БД.
- **`/info`** повертає `app` (з ConfigMap → доказ пункту 5d), `version` (з образу → пункт 6c) і `pod` (`socket.gethostname()` = ім'я пода → пункт 6b). Секретів не повертає.

### `app_version` (`config.py`) + `ARG/ENV APP_VERSION` (`Dockerfile`)
- `ARG` існує лише під час збірки, `ENV` — під час роботи; ланцюжок `ARG → ENV` «запікає» версію в образ, тож тег і вміст `/info` завжди збігаються.
- Не в ConfigMap, бо версія — властивість **образу**, а не середовища: інакше можна було б запустити 1.0.0 з написом «1.1.0».
- Рядки стоять наприкінці Dockerfile: `ARG/ENV` змінюють лише метадані, тому всі файлові шари беруться з кешу — друга версія збирається за секунди.

### Advisory lock у міграціях (`alembic/env.py`)
- Контейнер стартує командою `alembic upgrade head && uvicorn …`. При 2+ репліках на чистій БД обидва поди одночасно створювали б таблиці — один падав би з «already exists».
- `pg_advisory_lock(7262001)` — м'ютекс Postgres за числовим ключем: перший под мігрує, другий чекає й бачить, що схема вже на `head`.
- Сесійний lock (а не `_xact_`) тримається до закриття з'єднання — тобто до кінця всіх міграцій. `commit()` після нього закриває автотранзакцію SQLAlchemy 2.0, щоб alembic відкрив власну; на сесійний lock commit не впливає.
- Альтернатива — окремий `Job` для міграцій — правильніша для продакшену, але Job незмінний (immutable) і його треба перестворювати при кожному оновленні, що суперечить вимозі «одна команда `kubectl apply -f k8s/`».
- Ефект підтверджено: міграції виконав лише один под, другий — 0 перезапусків.

## 3. Маніфести: навіщо кожен файл і чому так

**Загальні рішення**
- **Один файл — один об'єкт** (вимога 4a): зручний diff і точкові зміни.
- **Числові префікси** (`00-`, `10-`…): `kubectl apply -f k8s/` обробляє файли за алфавітом, а namespace має існувати раніше за об'єкти в ньому. Десятки групують компоненти: 1x — Postgres, 2x — Redis, 3x — RabbitMQ, 4x — API, 5x — worker.
- **Явний `namespace:`** у кожному об'єкті — маніфести не залежать від «поточного» namespace у kubectl.
- **Мітки `app.kubernetes.io/name` і `part-of`** — рекомендовані Kubernetes стандартні мітки.

### `00-namespace.yaml`
Ізолює об'єкти проєкту від системних (`kube-system`, `ingress-nginx`) і дозволяє прибрати все однією командою `kubectl delete namespace fleet-management` — так перевірено розгортання з нуля.

### `01-configmap.yaml`
- Ключі названо **точно** як змінні, які читає pydantic-settings (`APP_NAME` → `settings.app_name`), тому підключення — один рядок `envFrom`.
- Значення в лапках: у ConfigMap усі значення — рядки; без лапок YAML прочитав би `true`/`30` як bool/число, і apply відхилив би маніфест.
- `redis://redis:6379` — DNS-ім'я Service, а не IP, бо IP подів змінюються.
- `REDIS_URL` іде напряму в Redis, а не через toxiproxy (як у compose) — toxiproxy був потрібен лише для fault-injection у Лабі 2.

### `02-secret.yaml`
- `stringData` — значення відкритим текстом, Kubernetes сам кодує в base64 у поле `data`.
- Secret лежить у git, бо вимога «з нуля однією командою» потребує його в `k8s/`. Компроміс: значення явно лабораторні; gitleaks — `no leaks found`. У продакшені тут були б Sealed Secrets / External Secrets.
- Власний користувач RabbitMQ замість `guest`: `guest` за замовчуванням дозволено лише з localhost, а worker підключається з іншого пода.
- Паролі без `@ : /` — вони вставляються в URL підключення.

### `10-postgres-pvc.yaml`, `30-rabbitmq-pvc.yaml`
- Файлова система контейнера тимчасова: без PVC після видалення пода БД втратила б дані, а `durable`-черга — повідомлення (вимога 4g).
- `ReadWriteOnce`: БД і брокер не вміють безпечно писати з кількох процесів; hostPath у minikube підтримує лише цей режим.
- `storageClassName` не вказано → клас за замовчуванням `standard`, диск створюється автоматично (dynamic provisioning).

### `11-postgres-deployment.yaml`
- **`strategy: Recreate`**: при rolling update новий под стартує раніше за видалення старого — два Postgres на одному RWO-диску пошкодили б дані. Короткий простій БД безпечніший.
- **Deployment, а не StatefulSet**: StatefulSet — «канонічний» об'єкт для БД, але описує диск усередині себе (`volumeClaimTemplates`), а вимога 4g просить окремий PVC. Для однієї репліки Deployment + PVC + Recreate поводиться так само.
- **`PGDATA` у підкаталозі** `pgdata`: Postgres відмовляється ініціалізувати непорожній каталог (на деяких дисках у корені є `lost+found`).
- **`sh -c` у пробах**: `exec` запускає програму без оболонки, тож `$POSTGRES_USER` не підставився б.
- **`valueFrom` поштучно, а не `envFrom`**: образу Postgres потрібні лише 3 змінні, а не вся конфігурація застосунку.

### `12-postgres-service.yaml`, `21-redis-service.yaml`, `32-rabbitmq-service.yaml`
- Дають стабільні DNS-імена `postgres`, `redis`, `rabbitmq`, на які посилаються рядки підключення.
- `ClusterIP` — доступ лише всередині кластера (принцип найменших привілеїв). За потреби — тимчасово `kubectl port-forward`.
- У RabbitMQ два порти, тому вони іменовані (`amqp`, `management`) — при кількох портах імена обов'язкові.

### `20-redis-deployment.yaml`
- Без PVC: у проєкті Redis — **кеш** стану авто, джерело істини — БД і телеметрія.
- Стратегія за замовчуванням (RollingUpdate) — диска немає, конфлікту між подами немає.

### `31-rabbitmq-deployment.yaml`
- **`RABBITMQ_NODENAME=rabbit@localhost`**: RabbitMQ зберігає дані в каталозі з іменем вузла `rabbit@<hostname>`; у Deployment hostname = ім'я пода з випадковим суфіксом → після рестарту створювався б новий порожній каталог. Фіксоване ім'я робить дані на PVC справді постійними.
- `timeoutSeconds: 10` у пробах — `rabbitmq-diagnostics` запускає Erlang-клієнт і працює повільно.
- Liveness `initialDelaySeconds: 60` > readiness 15: зарання спрацьована readiness лише не пускає трафік, а liveness **вбиває** контейнер — повільний брокер ніколи б не встиг стартувати.

### `40-api-deployment.yaml` — головний файл
| Налаштування | Навіщо |
|---|---|
| `replicas: 2` | Вимога 4b; падіння одного пода не зупиняє сервіс |
| `maxSurge: 1`, `maxUnavailable: 0` | Старий под видаляється лише після того, як новий став Ready → оновлення без простою (6e) і захист від битого образу (7a) |
| `revisionHistoryLimit: 5` | Скільки старих ReplicaSet зберігати для `rollout undo` |
| `startupProbe` на `/livez` (до 60 с) | Час на міграції при старті; поки не пройде — liveness/readiness не запускаються |
| `readinessProbe` на `/health` | Перевіряє і БД: при її недоступності под виходить із Service, але **не** перезапускається |
| `livenessProbe` на `/livez` | Лише «процес живий» — перезапуск має сенс тільки при зависанні самого процесу |
| `preStop: sleep 5` | Видалення пода одночасно шле SIGTERM і прибирає под з endpoints; друге поширюється із затримкою. Пауза закриває «вікно гонки» — жоден запит не потрапляє на под, що завершується |
| initContainer `wait-for-postgres` | `apply` створює все одночасно; без очікування alembic падав би, а контейнер ішов би в `CrashLoopBackOff` з наростаючими паузами |
| `pg_isready -U "$POSTGRES_USER"` | Виправлення реальної проблеми: з `runAsUser: 1000` в образі postgres немає користувача з таким UID, і без `-U` утиліта завершувалась кодом 3 |
| `envFrom` ConfigMap + `secretKeyRef` поштучно | Усі несекретні параметри одним рядком; секрети — явно перелічені (мінімальні права) |
| `DATABASE_URL` через `$(VAR)` | Kubernetes підставляє раніше визначені змінні — пароль зберігається в одному місці (Secret) |
| `imagePullPolicy: IfNotPresent` | Образ завантажено в minikube, у реєстрі його немає; `Always` щоразу ламав би запуск |
| `runAsNonRoot` + `runAsUser: 1000` | У Dockerfile `USER appuser` — ім'я, яке kubelet не може перевірити на «не root»; числовий UID знімає проблему |
| `allowPrivilegeEscalation: false` | Процес не може отримати більше прав, ніж має |

### `41-api-service.yaml`
- Типи Service: `ClusterIP` (лише всередині) → `NodePort` (+ порт на вузлі) → `LoadBalancer` (+ зовнішній балансувальник).
- `NodePort` закриває вимогу 4c — доступ і всередині кластера, і з хоста; заодно це запасний вхід, якщо Ingress недоступний.
- `targetPort: http` (іменований порт) — при зміні порту в контейнері правиться лише Deployment.
- Фіксований `nodePort: 30080` — однаковий номер у README і звіті.

### `42-api-ingress.yaml`
- Ingress — HTTP-рівень: домени, шляхи, TLS, один вхід на багато сервісів. Для веб-API природніший за «сирий» NodePort.
- Сам Ingress — лише правила; виконує їх контролер ingress-nginx (`minikube addons enable ingress`).
- nginx розподіляє запити round-robin — тому розподіл трафіку (6b) видно наочно.
- Доказ, що маршрутизація працює саме за правилом: запит без `Host: fleet.local` → 404.

### `50-worker-deployment.yaml`
- Worker — друга частина застосунку (телеметрія → стан авто); без нього застосунок неповний.
- Без проб: HTTP-сервера немає. При недоступному RabbitMQ код робить 10 спроб і завершується з помилкою — Kubernetes перезапускає контейнер, що фактично працює як liveness. У логах видно, як worker дочекався брокера (`attempt 7/10` → `Consuming queue 'telemetry'`).
- Без init-контейнера: worker сам уміє чекати RabbitMQ, а до БД звертається лише при обробці повідомлень.

## 4. Чому саме такі способи демонстрації

| Пункт | Підхід | Чому |
|---|---|---|
| 1b | `minikube image load` | Runtime вузла — containerd, він не бачить образи Docker Desktop. Варіант «локально завантажений у minikube» явно дозволено; GHCR-пакет приватний і потребував би `imagePullSecret` |
| 5a | `kubectl apply -f k8s/` | Декларативна й ідемпотентна команда; `create` падає на існуючих об'єктах і не оновлює їх |
| 5c | Ingress + NodePort + DNS у кластері | Показує всі три шляхи доступу; бізнес-сценарій (реєстрація → логін → `/auth/me`) доводить роботу з БД і Secret |
| 5d | `printenv` для ConfigMap, `describe` для джерел Secret | `describe` показує, звідки береться секрет, не розкриваючи значення |
| 6b | 40 запитів скриптом | Браузер тримає keep-alive з'єднання — статистика була б спотвореною |
| 6c/6d | `kubernetes.io/change-cause` через `annotate` | Прапорець `--record` застарів; анотація в YAML копіювалась би в наступні ревізії з неправильним текстом |
| 6e | Монітор: запит кожні 0,2 с з таймаутом 2 с | Об'єктивний доказ: кількість збоїв = 0, а не «на око» |
| 7 | Тег `9.9.9` | Тегу немає ні у вузлі, ні в Docker Hub → гарантований `ImagePullBackOff` |
| 7c | Логи пода з битим образом | Демонструє, що при `ImagePullBackOff` логів немає — причину треба шукати в Events |
| 7d | `rollout undo` | Показує, навіщо зберігається історія ревізій |

## 5. Відомі нюанси

- **`kubectl apply -f k8s/` після `scale`/`set image`/`undo`** поверне значення з YAML (2 репліки, образ 1.0.0) — це очікувана поведінка декларативного підходу. Попередження `last-applied-configuration` при `rollout undo` нагадує саме про це.
- **`kubectl apply --dry-run=server` на чистому кластері** повідомляє `namespace not found` для всіх об'єктів, крім namespace: у dry-run namespace створюється лише «уявно». На кластері з існуючим namespace dry-run працює повністю.
- **Windows + драйвер docker**: вузол minikube у мережі Docker, яку хост не бачить напряму. Для Ingress потрібен `minikube tunnel` — він прокидає порт 80 ingress-контролера на `127.0.0.1` і працює у звичайному терміналі (одночасно може працювати лише один тунель — інакше `TUNNEL_ALREADY_RUNNING`). Права адміністратора потрібні лише для запису `127.0.0.1 fleet.local` у `C:\Windows\System32\drivers\etc\hosts` — локальний «довідник» імен, без якого браузер не знає, куди веде вигадане ім'я `fleet.local` (`curl`/`Invoke-RestMethod` обходяться без нього, передаючи заголовок `Host` вручну). Для NodePort — `minikube service api -n fleet-management --url`, без адміністратора й без `hosts`.
