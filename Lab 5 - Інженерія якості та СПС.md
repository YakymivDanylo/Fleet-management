# **ЛАБОРАТОРНА РОБОТА №5** 

# **Проєктування Enterprise-стратегії інженерного аудиту за парадигмою GQM та інфраструктурна валідація метрик** 

**Мета роботи:** Набути практичних навичок стратегічного планування інженерного аудиту та розгортання корпоративних систем контролю якості (Software Quality Governance); опанувати дедуктивну методологію «GoalQuestion-Metric» (GQM) для декомпозиції верхньорівневих бізнес-цілей у вимірювані інженерні показники на трьох незалежних контурах: продукт, процес та команда; навчитися класифікувати збирані метрики коду за рівнями шкал вимірювань Стівенса та математично обґрунтовувати валідні операції статистичного аналізу; дослідити управлінські ризики Закону Гудхарта та спроєктувати архітектурні метрики-балансири для нейтралізації штучного маніпулювання даними; опанувати інфраструктурні методики проведення стрес-тестів засобів статичного та динамічного аналізу на надійність (Reliability) і стабільність (Stability) у неізольованих середовищах розгортання софту. 

**Інструментарій:** 

- Static Code Analyzers (на вибір під стек проєкту): Lizard CLI (pip install lizard), Radon CLI (Python), TyphonJS Escomplex (JavaScript/TypeScript), PhpMetrics (PHP) або Microsoft.CodeAnalysis.Metrics (.NET). 

- Mutation Testing Frameworks (на вибір): Stryker Mutator (JS/TS, C#, broken Python support), Pitest (Java), Mutation-Informer/Mutmut (Python). 

- DevOps & Infrastructure: Docker Community Edition (Engine/Desktop), Git CLI. 

**Об'єкт дослідження:** Студент продовжує розвивати, аналізувати та супроводжувати свій індивідуальний програмний проєкт (наприклад, вебсервіс, API-модуль, Telegram-бот), який він розгортав та інтегрував із засобами контролю якості в ЛР№1–4. 

# **ПОРЯДОК ВИКОНАННЯ ЗАВДАНЬ** 

# **Завдання 1. Дедуктивне проєктування Enterprise-матриці вимірювань GQM та паспортизація шкал Стівенса** 

Студент має піднятися з позиції рядового розробника на рівень вищого технічного менеджменту (Software Quality Governance) і довести, що кожна метрика у його репозиторії підпорядкована комерційним або архітектурним цілям компанії. 

# **_Покроковий алгоритм виконання:_** 

# 1. Декларація стратегічної мети (Goal): 

Сформулювати одну високорівневу інженерну ціль для свого проєкту. Формулювання має строго відповідати класичному п'ятикомпонентному інженерному шаблону Віктора Басілі: 

   - Об'єкт дослідження: (наприклад: підсистема логістики, API ядра, платіжний модуль). 

   - Ціль: (оцінити, спрогнозувати, оптимізувати, покращити). 

   - Якісний фокус: (надійність, супроводжуваність, безпека, часова поведінка). 

   - Роль / Позиція: (з позиції Lead Software Architect або Enterprise QA Manager). 

   - Контекст середовища: (у межах фіксованого таймлайну розробки MVP, ітераційного спринту тощо). 

2. Розгортання дерева запитань (Questions): 

Для сформульованої мети розробити строго 6 інженерних запитань – по 2 запитання на кожен із трьох корпоративних контурів вимірювання: 

- Контур 1: Продукт (Product Quality) – запитання про внутрішню чистоту коду, зачеплення, архітектурні залежності та вразливості. 

- Контур 2: Процес (Process Efficiency) – запитання про стабільність пайплайнів, динаміку тестування, частоту збоїв розгортання та швидкість виправлення. 

- Контур 3: Команда та Ресурси (Team Productivity) – запитання про капіталізацію технічного боргу, трудовитрати на рефакторинг та комплаєнс-навантаження інженерів. 

# 3. Мапування на виконувані метрики (Metrics): 

Під кожне з 6 запитань підібрати щонайменше одну точну інженерну метрику, яка може збиратися автоматично або напівавтоматично існуючим інструментарієм (SonarQube API, Git CLI log, звіти k6, Mend/Snyk, Gitleaks логи). 

4. Математична паспортизація за Стівенсом: 

Усі 6 спроєктованих метрик необхідно розподілити за чотирма класичними шкалами вимірювань (Стівенса): 

   - Номінальна шкала (категорії, типи компонентів, технологічні стеки). 

   - Порядкова шкала (рейтинги надійності A/B/C/D, пріоритети багів, рівні критичності CVE). 

   - Інтервальна шкала (часові мітки, дати релізів, відносні зсуви). 

   - Відносна шкала (цикломатична складність, час відгуку в мс, технічний борг у годинах, % покриття тестами). 

5. Математичне обґрунтування агрегації: 

Для кожної метрики надати коротке аналітичне обґрунтування допустимих операцій (статистичних та математичних), які можуть застосовуватись до кожної метрики при аналізі великих звітів. Студент повинен чітко продемонструвати розуміння обмежень шкал: 

- Чому не можна рахувати середнє арифметичне для порядкових оцінок (наприклад, Security Rating = A та Security Rating = C не дають у середньому «B»). 

- Які агрегації (медіана, перцентилі, середнє арифметичне) є валідними для його відносних мір (наприклад, чому для часу відгуку під навантаженням використовується 95-й перцентиль, а не середнє значення). 

# **_Очікуваний результат завдання №1 у звіті_** 

- Декларація стратегічної мети: Офіційне формулювання інженерної цілі проєкту за суворим шаблоном Басілі (із зазначенням об'єкта, ролі та якісного фокусу). 

- Паспорт інженерних вимірювань (GQM Matrix): Зведена ієрархічна таблиця, що демонструє дедуктивний зв'язок від бізнес-цілей до коду: Контур вимірювання | Інженерне запитання (Q) | Технічна метрика (M) | Шкала Стівенса | Валідна математична агрегація 

- Архітектурно-математичне обґрунтування: Короткий аналітичний коментар студента, що доводить розуміння обмежень шкал (наприклад, критичне пояснення, чому обчислення середнього арифметичного значення для порядкових рейтингів безпеки SonarQube A та C є методологічною помилкою інженера). 

# **Завдання 2. Стрес-тест комплаєнсу на Закон Гудхарта та проєктування метрикбалансирів** 

Менеджерський та психологічний контур Quality Governance. Студент повинен подивитися на власну стратегію вимірювань очима розробника, який намагається обійти встановлені правила якості. 

# **_Покроковий алгоритм виконання:_** 

# 1. Моделювання архітектурного краш-сценарію (Пастка Гудхарта): 

Обрати зі свого дерева GQM (із Завд.1) одну ключову кількісну метрику з контуру продукту або процесу (наприклад, Test Line Coverage %, Fixed Bugs Count, Cyclomatic Complexity). Описати реалістичний сценарій деградації архітектури системи, якщо вище керівництво (PM/Product Owner) перетворить цю метрику на головний KPI команди або прив'яже до неї фінансові бонуси. Студент має текстово показати, як розробники зможуть штучно «підігнати» цю цифру під зелену зону Quality Gate (наприклад, написання unit-тестів без assert для накрутки Coverage), суттєво погіршивши при цьому реальну якість софту. 

2. Проєктування інженерної метрики-балансира (Compensating Metric): 

Для повної нейтралізації змодельованого «хакінгу» ввести в архітектуру контролю якості другу, компенсаційну метрику. Метрика-балансир має діяти за принципом системи стримувань і противаг: вона повинна робити штучне підганяння першої метрики технічно або економічно неможливим для програміста. 

Орієнтир: Якщо перша метрика міряє кількість рядків коду (LOC), балансир має міряти щільність або якість. Якщо перша метрика міряє покриття тестами (Test Coverage), балансир має міряти реальну здатність тестів знаходити баги за допомогою мутаційного аналізу (Mutation Score через Stryker Mutator / Pitest). 

3. Створення збалансованого Quality Gate: 

Інтегрувати обидві метрики в єдине логічне комбіноване правило для автоматизованих «воріт якості» вашого проєкту. Записати підсумкову формулу з конкретними граничними значеннями (Thresholds), використовуючи суворий логічний оператор AND. Система має проходити валідацію (PASS) лише тоді, коли обидва індикатори перебувають у балансі. 

# **_Очікуваний результат завдання №2 у звіті студента_** 

- Аналітична декларація ризику: Чіткий текстовий опис пастки закону Гудхарта для обраної метрики вашого проєкту (як розробники можуть обійти автоматику та які наслідки це матиме для кодової бази). 

- Специфікація метрики-балансира: Технічний опис компенсаційної міри: її назва, призначення та безкоштовний інструментарій, яким вона збирається (Stryker, Lizard, Git CLI тощо). 

- Архітектурний щит комплаєнсу (Balanced Quality Gate): Логічна формула воріт якості з обґрунтованими порогами відсікання. Приклад: (New Code Line Coverage >= 80%) AND (New Code Mutation Score >= 65%). 

# **Завдання 3. Інфраструктурний краш-тест засобів аналізу на надійність та стабільність** 

Студент спускається на рівень DevOps-інфраструктури розгортання та перевіряє, чи можна беззастережно довіряти цифрам, які видає автоматика в CI/CD пайплайнах, та як заізолювати середовище збору від сторонніх інфраструктурних шумів. 

# **_Покроковий алгоритм виконання:_** 

1. Експеримент 1: Верифікація надійності інструменту (Reliability Test): 

Студент має перевірити, чи однаково інструмент статичного аналізу рахує метрики для одного й того самого файлу коду при зміні параметрів оточення. 

- Дія: Взяти один із найбільш заплутаних файлів коду свого проєкту. Штучно змінити налаштування системи/файлу, які не змінюють бізнес-логіку та алгоритм: 

   - Сценарій А (Форматування ОС): Змінити кодування файлу або символи закінчення рядків (перевести файл із формату Windows CRLF у Unix LF або навпаки). 

   - Сценарій Б (Версійність): Змінити версію інтерпретатора, компілятора чи Dockerобразу раннера, під яким виконується CLI-сканер (наприклад, сканувати код за допомогою Radon/Lizard спочатку під Node.js/Python старої LTS-версії, а потім – під найновішою). 

- Аналіз: Зафіксувати метрики рядків коду (LOC), когнітивної складності чи Code Smells. Документально підтвердити, чи залишилися числа абсолютно ідентичними. 

2. Експеримент 2: Верифікація стабільності метрик (Stability Test): 

Студент перевіряє , чи реагують його налаштовані інженерні дашборди виключно на фізичні зміни у кодовій базі, чи на них впливають сторонні інфраструктурні шуми та перевантаження заліза. 

- Дія: Симулювати неізольоване середовище під час збору динамічних або статичних метрик. 

   - Якщо використовуються динамічні метрики (наприклад, час відгуку p95 через k6/JMeter з ЛР№2) – запустити навантажувальний тест спочатку в ізольованому середовищі, а потім повторити його, паралельно запустивши на цій же машині важкий сторонній процес (важка компресія логів, штучне обмеження CPU Core для контейнера додатка через Docker флаги --cpus). 

   - Якщо використовуються статичні метрики (SonarQube/Lizard) – запустити паралельно два важких процеси сканування в умовах жорсткого ліміту RAM раннера. 

- Аналіз: Зафіксувати флуктуації (сплески) метрик. Продемонструвати, як сторонній інфраструктурний шум спотворює графіки, викликаючи помилковий FAIL у Quality Gate, хоча сам код працює ідентично. 

3. Технічна декларація інженерного захисту: 

На основі проведених експериментів сформулювати та впровадити у свій проєкт набір інфраструктурних заходів захисту вимірювань від спотворень (наприклад: жорстка фіксація версій лінтерів у конфігах, контейнеризація засобів аналізу з лімітуванням ресурсів раннерів cpus/memory). 

# **_Очікуваний результат завдання №3 у звіті_** 

- Протокол тесту на надійність (Reliability Report): Порівняльна таблиця метрик статичного аналізу файлу коду до і після зміни умов середовища (версії компілятора чи символів переносу рядків). Оцінка стійкості інструменту. 

- Метричний профіль стабільності (Stability Crash-Test): Графіки або порівняльні таблиці показників (наприклад, p95 Response Time, Error Rate, RAM usage) в ізольованому стані (PASS) та в умовах штучного стороннього шуму (Failed / Хибне спрацювання). 

- Технічна декларація інженерного захисту: Перелік архітектурних та інфраструктурних заходів, які студент впровадив у свій проєкт для захисту від помилок вимірювань (наприклад: фіксація версій лінтерів у файлі конфігурації, використання Dockerконтейнеризації з жорсткими лімітами cpus і memory для раннерів CI/CD). 

# **ВИМОГИ ДО ОФОРМЛЕННЯ ЗВІТУ** 

У підсумковому Project Hub-звіті студент повинен представити (Notion / Obsidian / тощо): 

- Паспорт інженерних вимірювань (GQM Matrix): Зведена ієрархічна таблиця: Контур вимірювання (Продукт/Процес/Команда) | Інженерне запитання (Q1-Q6) | Технічна метрика (M1-M6) | Шкала Стівенса | Валідна математична агрегація. 

- Архітектурно-математичне обґрунтування: Короткий аналітичний коментар, що доводить розуміння обмежень шкал Стівенса та методологічних помилок при розрахунку мір центральної тенденції. 

- Аналітична декларація ризику (Гудхарт): Текстовий опис краш-сценарію маніпулювання метрикою та технічна специфікація обраної метрики-балансира із зазначенням безкоштовного інструменту її автоматизації. 

- Архітектурний щит комплаєнсу: Логічна формула комбінованого Quality Gate з обґрунтованими порогами відсікання. 

- Протокол тесту на надійність та стабільність (DevOps Report): Порівняльні таблиці або графіки флуктуацій метрик у чистому стані (PASS) та в умовах стороннього інфраструктурного шуму (Хибний FAIL). 

# **КРИТЕРІЇ ОЦІНЮВАННЯ (Максимум: 10 балів)** 

Завдання 1 – 3 бали: 

- 3 бали: Стратегічна мета сформульована бездоганно за шаблоном Басілі. Дерево GQM повністю розгорнуто на три контури (6 запитань, 6 метрик), шкали Стівенса визначені математично точно для всіх показників, а обмеження на операції агрегації повністю обґрунтовані у звіті. 

- 1.5 бали: Дерево GQM побудовано, але пропущено один із контурів (наприклад, немає командних метрик), або припустилися помилок у визначенні шкал вимірювань (наприклад, відносна метрика часу відгуку помилково занесена до порядкової шкали). 

- 0 балів: Завдання не виконано, або структура GQM повністю відсутня. 

Завдання 2 – 3 бали: 

- 3 бали: Краш-сценарій закону Гудхарта змоделовано зріло та реалістично. Метрику-балансир підібрано технічно коректно з чітким зазначенням інструменту її автоматизації. Формула комбінованого Quality Gate повністю усуває ризики маніпулювання даними. 

- 1.5 бали: Описано пастку закону Гудхарта, але запропонований балансир не вирішує проблему (наприклад, як противагу до рядків коду LOC пропонується міряти кількість коментарів). Або формула Quality Gate сформована без реальних інструментальних порогів. 

- 0 балів: Завдання не виконано, або аналіз валідності відсутній. 

Завдання 3 – 4 бали: 

- 4 бали: Обидва експерименти (надійність та стабільність) проведені повністю, результати зафіксовані у вигляді порівняльних таблиць або графіків флуктуацій. Студент продемонстрував розуміння інфраструктурних ризиків та надав зрілі технічні рекомендації щодо ізоляції середовища в CI/CD. 

- 2 бали: Проведено лише один експеримент (або надійність, або стабільність), або результати мають поверхневий характер без аналізу причин коливання чисел. 

- 0 балів: Завдання не виконано, стрес-тест системи вимірювань відсутній. 

Штрафні бали (при захисті у форматі Live Demo): 

- –2 бали: Студент не може усно пояснити різницю між інтервальною та відносною шкалами вимірювань або плутає математичний зміст медіани та середнього арифметичного. 

- –3 бали: Студент не надав лог взаємодії з ШІ або лог демонструє, що ШІ виконав дедуктивний аналіз GQM замість студента (порушення регламенту Техліда).
